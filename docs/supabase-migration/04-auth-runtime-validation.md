# Supabase authentication runtime validation

Status: `PARTIAL — bridge deployed and server-smoke-validated; controlled device validation pending`.

## Owner-app runtime contract

The owner app uses Supabase Auth as its new session authority while retaining a Firebase Auth compatibility session for the still-Firebase-backed Firestore, Storage, callable Functions, FCM-token, and billing paths. The Supabase client contains only the hosted project URL and public anon key. A service-role key is never placed in Android configuration.

- Password login uses the deterministic alias `phone-<canonical-63-digit-phone>@auth.aquahub.app`.
- During migration, the app proves an existing Firebase password credential, then claims or signs into the matching Supabase password account. Firebase users are not deleted.
- Google login uses the web OAuth client ID generated as `R.string.default_web_client_id` from `AquaHub/app/google-services.json`, then signs into both Supabase and Firebase compatibility sessions.
- `public.profiles.firebase_uid` is read and validated, but is not writable by the Android client. A null mapping temporarily falls back to the Firebase compatibility UID; a conflicting non-null mapping is rejected.
- The Supabase profile role is authoritative only when the mapping is present and valid. Legacy Firestore role data remains the explicit fallback until backfill is complete.

## Provider and configuration checklist

The Firebase configuration contains the owner package `com.aesprt.aquahub`, Android OAuth client entries, and a web OAuth client entry. The app passes the generated web client ID to Credential Manager; the Android client IDs and signing fingerprints remain in Firebase configuration and are not duplicated in source or documentation.

### Supabase Dashboard configuration

- Phone: enable Phone provider; configure a supported SMS provider such as Twilio, MessageBird, or Vonage; verify Philippine (+63) delivery and sender requirements with the provider. Supabase's documented default is one OTP request per 60 seconds with a one-hour expiry; the current Android UI accepts a 4–10 character code and must be tested against the provider's actual six-digit OTP. Configure CAPTCHA/rate limits before production SMS use.
- Email: keep Email provider and password sign-in enabled; keep email confirmation enabled; configure recovery emails and the confirmation/recovery templates; configure custom SMTP for production rather than relying on the hosted trial sender.
- Google: enable Google provider and configure the Google Web OAuth client ID/secret. The current Android code uses Credential Manager to obtain the Web client ID token and calls Supabase `signInWith(IDToken, provider=Google)`, so it does not use a browser OAuth callback. Register the Android application in the Google project with its package name and signing SHA-1/SHA-256 as required by Google/Firebase; keep the Web client ID in the existing Firebase configuration.

### Redirect allowlist

Add exactly these Supabase redirect URLs:

- `aquahub://auth/recovery` — password recovery; handled by `PasswordRecoveryActivity`.
- `aquahub://auth/confirm` — email confirmation; handled by the same activity and displayed as a completed verification state.

No Google redirect URL is used by the current native ID-token implementation. If the implementation later changes to browser OAuth, add only the callback URL generated by Supabase and register that same callback in Google Cloud; do not pre-authorize an unimplemented URL.

### Firebase bridge secrets/deployment

`issueFirebaseCompatibilityToken` declares and binds `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` with Firebase Secret Manager. The hosted deployment is validated in `asia-southeast1`; secret values remain out of source, logs, and Android. For future rotation, use interactive secret entry only:

```bash
cd AquaHubCustomer
firebase functions:secrets:set SUPABASE_URL --project aquahub-506411
firebase functions:secrets:set SUPABASE_SERVICE_ROLE_KEY --project aquahub-506411
firebase deploy --only functions:issueFirebaseCompatibilityToken --project aquahub-506411
```

Never pass the service-role value as a command-line argument, commit generated `.env.*` files, or place it in Android configuration. `functions/.gitignore` now excludes generated secret environment files.

Before device validation, configure the hosted Supabase project with:

1. `SUPABASE_URL` and `SUPABASE_ANON_KEY` in the developer's untracked `AquaHub/local.properties` or build environment. Release builds fail closed when either is absent.
2. Google provider enabled with the same web OAuth client ID used by `default_web_client_id`, plus the Supabase dashboard callback URLs.
3. Email confirmation behavior suitable for the deterministic phone-alias migration flow, or an approved server-side account-claim process. Password recovery currently requires an email-capable alias/recovery address; phone aliases are not recoverable through a normal email link.
4. Firebase Android OAuth clients and signing fingerprints unchanged for the compatibility session.

## Auth email provider and rate limits

The hosted fixture signup returned `over_email_send_rate_limit`. This is an Auth email-delivery limit, not an RLS failure. Do not disable abuse protection or raise limits merely to make fixtures pass.

- Custom SMTP is recommended before production password recovery so delivery, sender identity, bounce handling, and operational quotas are controlled by AquaHub. Configure it manually in Supabase Auth; no provider credentials belong in the repository or Android app.
- Review the hosted project's Auth email rate limits, resend windows, CAPTCHA/abuse controls, and confirmation settings manually. Exact quotas and dashboard fields are deployment-specific and were not changed automatically.
- For development, use pre-created email-confirmed disposable users through the protected fixture mode, a dedicated test project, or a controlled SMTP test inbox. Never bulk-send test emails to real users.
- Production recommendation: retain confirmation and abuse controls for human recovery addresses, disable confirmation only for the internal deterministic phone aliases if that is an explicitly approved migration decision, and use the staged Firebase-credential proof/claim flow for existing users.

The Android recovery deep link is now implemented as `aquahub://auth/recovery` and handled by `PasswordRecoveryActivity`. The activity accepts only the Supabase Auth callback for the current recovery session, updates that session's password, and signs out Firebase compatibility state before closing. It does not accept a Firebase UID from the URL or perform an account claim. Configure the exact URI in Supabase Auth URL configuration and test both cold-start and already-running-app delivery on a device.

## Identity backfill

Use `supabase/scripts/backfill_firebase_identities.py` with an authorized Firebase Auth export. It is dry-run-first and never prints credentials. `--apply` requires both `SUPABASE_SERVICE_ROLE_KEY` and `--confirm-production-backfill`; it only updates unambiguous `READY` `profiles.firebase_uid` mappings and can write a mode-600 audit report. It refuses duplicate Firebase UIDs, duplicate email/phone aliases, missing profiles, conflicting existing mappings, and unknown legacy roles. It never deletes Firebase users. The production dry run found 24 Firebase users, 0 Supabase users, and 0 profiles, so no apply run is safe yet; see `05-production-identity-backfill.md`.

Example dry run:

```text
python3 supabase/scripts/backfill_firebase_identities.py \
  --firebase-export /secure/path/firebase-auth-export.json
```

Review every `READY`, `ALREADY_MAPPED`, `MISSING_SUPABASE_USER`, `MISSING_FIREBASE_USER`, `AMBIGUOUS`, `UID_CONFLICT`, `ALIAS_CONFLICT`, `UNKNOWN_ROLE`, `MISSING_PROFILE`, and `FAILED` result before any apply run. Role updates are limited to the known enum values `OWNER`, `MANAGER`, `STAFF`, `RIDER`, and `CUSTOMER`.

The separate Auth-user staging dry run found 20 `PHONE_ALIAS_PASSWORD` users and 4 `GOOGLE` users; all 24 are `MANUAL_REVIEW`. No password hashes, provider identities, profiles, roles, or Firebase UIDs were staged; see `06-auth-user-staging.md`.

`supabase/scripts/hosted_rls_fixtures.py` provisions six disposable users, seeds two organizations and assigned stations through the linked admin connection, exercises the public REST API with each user's JWT, and cleans up its own fixtures. The assertions passed against hosted project `pfkxrggexueltytxtqil`:

- organization A/B isolation for owners;
- manager and assigned-staff reads;
- customer denial of protected organization reads;
- station assignment isolation;
- customer membership insert denial;
- protected profile-role update denial;
- manager ownership-field update denial;

The first public-signup attempt was blocked by Supabase Auth's disposable email-send rate limit (`over_email_send_rate_limit`). The completed validation used the script's explicit service-role fixture mode to create email-confirmed disposable users in-process, then authenticated through the public password-token endpoint. Cleanup initially hit a transient CLI login-role initialization error; authenticated REST cleanup completed and verified zero remaining `codex-rls-*` users and zero `Codex RLS Fixture` organizations.

This validates the current schema policies, not the Android UI. A physical-device pass is still required for password login/claim, Google login, session restore, logout, password recovery/deep-link handling, FCM token dual-write, Analytics, and Crashlytics.

## Device checklist

Password user: new signup; existing Firebase-user claim; login; wrong password; logout; restart/session restore; token refresh; recovery link; password reset.

Google: new login; existing login; no duplicate profile; restart/session restore; logout/re-login.

Identity: Supabase UID, `firebase_uid`, and role are correct; legacy Firestore data still loads; logout leaves no previous-account identity.

FCM: token registration, refresh, Supabase device mapping, push delivery, and logout handling.

Analytics: login and signup events are visible.

Crashlytics: Supabase UID is assigned and cleared on logout; no sensitive data is logged.

## Firebase Auth compatibility inventory

Firebase Auth remains required by the owner app until the corresponding business modules migrate: Firestore sync/listeners and outbox writes, Firebase Storage paths, FCM token compatibility writes, callable Functions and billing, owner legacy profile/business context, and onboarding phone verification. No current Firebase Auth reference can be removed safely without changing those paths. After each module migrates, re-audit and replace its UID dependency with the server-issued compatibility mechanism or remove it as part of the final Firestore cutover.
